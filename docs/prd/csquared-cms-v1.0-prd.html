Section 01

Executive Summary

CSquared's Change Management System (CMS) is an internal web application that replaces the current Google Forms-based infrastructure change request process with a structured, auditable, role-based workflow spanning all six African OpCos.

ISO 27001 Certification Context CSquared is actively pursuing ISO 27001 certification. This system is required evidence for control A.12.1.2 (Change Management). The absence of an auditable change management system is a current gap in the certification evidence package. Delivery of v1.0 is on the critical path for certification.

The Problem

Infrastructure changes across Ghana, Uganda, DRC, Togo, Liberia, and Mauritius are currently initiated via a Google Form that routes submissions to email. This process has no enforcement of approval workflows, no immutable audit trail, no role-based access control, and no visibility across OpCos for group-level stakeholders.

The Solution

A Next.js web application backed by PostgreSQL and Keycloak (IAM) that provides the complete change lifecycle — from drafting and submission through multi-level approval, implementation tracking, and audit evidence export — with strict per-OpCo data isolation and a group-level view for cross-OpCo administrators and auditors.

Section 02

Background & Problem Statement

Current State

Engineers across all OpCos use a shared Google Form modeled on the CSquared Technical Change Request document. Submissions arrive in a shared inbox and are routed manually by email for approval. There is no system-enforced approval gate, no escalation path, no status tracking after submission, and no queryable audit trail.

Pain Points by Role

RolePain PointBusiness Impact
RequesterNo visibility into approval status after submitting. Must chase approvers over Slack or email.Delays in change execution; shadow changes proceed without approval.
ApproverNo central inbox — approvals buried in email. No context on risk level or previous decisions.High-risk changes approved without due diligence; SLA breaches.
AuditorNo queryable audit trail. Evidence must be assembled manually from email threads and spreadsheets.ISO 27001 A.12.1.2 control cannot be evidenced. Certification risk.
AdminNo user management. Cannot onboard engineers to a structured access model or revoke access centrally.Stale access, no segregation of duties.
Group LeadershipNo cross-OpCo visibility. Cannot see change volumes, risk trends, or outstanding approvals across all markets.Operational blind spot; no group-level reporting for executive audiences.

ISO 27001 A.12.1.2 Requirements This System Must Satisfy

  • Documented change procedure — a defined workflow from request to closure, enforced by the system
  • Risk assessment on all changes — structured risk level classification (low / medium / high / emergency) captured at submission
  • Approval before implementation — system-enforced gate; no change can move to "implemented" without an approved record
  • Impact analysis — required fields for impact scope, implementation plan, testing plan, and backout plan
  • Segregation of duties — requesters cannot approve their own changes; enforced at the API layer
  • Immutable audit trail — append-only log of every state transition, actor, and timestamp
  • Exportable evidence — CSV and PDF exports for auditor review packages

Multi-Tenant Organization Model

Foundational Architecture Decision The entire system is built around this two-tier tenancy model. Every resource (change requests, approvals, users, teams, reports) is tagged with an opcoId. Data isolation is enforced at the API query layer — not just the UI — so an OpCo-scoped user cannot retrieve another OpCo's data even with direct API calls.

Access Tiers

OpCo-scoped users belong to exactly one OpCo. Their session is always in the context of that OpCo. They can see and operate on data for that OpCo only — regardless of their role.

Group-scoped users are assigned at the Group level with group_admin or group_auditor roles. They see data across all OpCos, navigate via an OpCo switcher in the header, and have access to a cross-OpCo Group Dashboard.

User–OpCo Assignment Model

A user may hold different roles in different OpCos. This is modeled via a UserOpCoAssignment join table — not a single country field on the user record. Examples:

  • Alice is approver in Ghana and auditor in Uganda (moved teams; historical access preserved)
  • Bob is group_admin at the Group level (access to all OpCos with admin privileges)
  • Carol is requester in Liberia only (narrowest scope)
UserOpCoAssignment {
  userId:    String        // FK → User
  opcoId:    String | null // null when role is group-scoped
  role:      Role          // requester | approver | auditor | admin | group_admin | group_auditor
  isActive:  Boolean
  startedAt: DateTime
  endedAt:   DateTime?     // null = still active; timestamped on deactivation or OpCo transfer
}

Section 06

User Lifecycle

Onboarding

  1. OpCo Admin (or Group Admin) opens the User Onboarding Wizard (3-step: Profile → Access → Teams)
  2. Assigns the user's name, work email, OpCo, role, permissions, and team memberships
  3. A Keycloak user record is created via the Keycloak Admin API; the Google Workspace IdP link is established
  4. An invitation email is sent; the user logs in via Google SSO (@csquared.com enforced at Keycloak)
  5. On first login, the JWT is consumed by Auth.js; the User record and UserOpCoAssignment are created/synced in PostgreSQL

Cross-OpCo Assignment

When an engineer gains access to a second OpCo (e.g., temporary project, secondment), a Group Admin creates a new UserOpCoAssignment row with a different opcoId and role. The user now appears in both OpCos' user lists. Their JWT token includes both OpCo memberships; the app presents an OpCo context switcher if they have more than one assignment.

Role Change

An Admin updates the user's role in Keycloak (organization role) and in the UserOpCoAssignment table. The change is logged in the audit trail. The new role takes effect on the user's next session token refresh (or immediately on forced re-login).

OpCo Transfer

When a user permanently moves to a different OpCo: the existing UserOpCoAssignment row has endedAt set (timestamped, preserving history) and isActive = false. A new assignment is created for the new OpCo. Historical change records referencing the old OpCo remain intact and auditable.

Deactivation / Offboarding

  1. Admin disables the user in Keycloak — active sessions are revoked immediately
  2. All UserOpCoAssignment rows for the user are set to isActive = false and endedAt = now()
  3. User cannot log in; all historical records (change requests, approvals, audit entries) are retained for audit integrity
  4. Any pending approval assignments are re-routed to the OpCo Admin or next available approver
Audit Integrity User records are never hard-deleted. The isActive flag governs login access. Historical records remain intact and attributable to the deactivated user, ensuring no audit gaps.

Delegation

An approver may delegate their approval authority to another approver within the same OpCo for a defined period (e.g., annual leave). Delegation is time-bounded (validFrom / validUntil) and can be revoked early by setting isActive = false. Delegated approvals are flagged in the approval record so auditors can distinguish direct from delegated decisions.

Change Advisory Board (CAB)

The CAB is a group-level construct. CAB members hold the approver role at the Group level, granting cross-OpCo approval authority for high-risk and emergency changes.

  • High-risk quorum: Minimum 2 CAB members must independently approve. Enforced at the API layer — a high-risk change cannot transition to approved until COUNT(approvals WHERE isCab = true AND decision = 'approve') >= 2
  • Emergency changes: Require CAB Chair or Group Admin approval (single approver, but at the highest authority level); bypasses the normal quorum requirement
  • CAB approval is async: No synchronous meeting required in v1.0. CAB members review and approve via the system directly

Blackout Period Enforcement

Admins define blackout periods (per-OpCo or group-wide) for maintenance freezes, end-of-quarter periods, or holiday windows.

  • Standard changes during blackout: Hard block. Submission is rejected with a clear error message stating the active blackout period and its end date
  • Emergency changes during blackout: Allowed via the Emergency override path. Requester explicitly marks the change as Emergency at submission. The system bypasses the blackout block, routes to the CAB Chair, and sends an immediate alert notification

Escalation

If an approval SLA is breached (no decision within the defined window), the system automatically escalates: first to the OpCo Admin, then (if still unresolved after another 50% of the original SLA period) to the Group Admin. All escalations are logged in the audit trail and trigger email notifications.

Rejection

A rejection comment is mandatory — enforced at both the UI (disabled submit button) and API layer (400 response if comment is absent). The requester receives an email notification with the rejection reason. The change returns to draft status and may be amended and re-submitted.

Section 09

Technical Architecture

Identity & Access
(Keycloak)
Keycloak 26+ — Single realm csquared. 6 Organizations (one per OpCo). Google Workspace as federated Identity Provider (@csquared.com enforced). Issues OIDC JWTs containing organizations (OpCo memberships + roles) and realm_roles (group-level roles) claims. Native event audit log for auth events (logins, token grants, role changes). Deployed as a Docker container — runs on Cloud Run or on-prem Kubernetes.
Application
(Next.js)
Next.js 16 (App Router) + TypeScript. Auth.js (NextAuth) with the Keycloak OIDC provider. Middleware verifies JWTs on every request — extracts opcoId and role; rejects unauthorized before reaching route handlers. Server Actions and API Routes handle all mutations; client components handle UI state only. Tailwind CSS v4 + shadcn/ui for the UI layer.
Data
(Prisma + PG)
Prisma v7 ORM with @prisma/adapter-pg driver adapter (no Prisma Accelerate dependency — portable). PostgreSQL as the primary database. All resource tables include opcoId; all Prisma queries filtered by the user's accessible OpCos from the JWT. AuditLog table is append-only by API convention. Prisma Migrate for schema versioning.
Storage
(S3-compat.)
File attachments stored in any S3-compatible object storage (AWS S3, GCS with S3 compatibility, MinIO for on-prem). Presigned URLs issued by the API for upload and download — files never proxy through the Next.js server. Attachment metadata (filename, storageKey, MIME type, size) stored in PostgreSQL.
Deployment
(Containers)
Platform-agnostic containerized deployment. No cloud-specific SDK dependencies. Compatible with GCP Cloud Run + Cloud SQL or on-prem Kubernetes. CI/CD pipeline (to be configured) runs lint, type-check, and Prisma migrate validation on every push.

Keycloak Multi-Tenancy Topology

Realm: csquared
├── Identity Provider: Google Workspace
│   └── Allowed domain: @csquared.com
├── Organizations (one per OpCo):
│   ├── ghana       → roles: requester, approver, auditor, admin

│   ├── drc         → roles: requester, approver, auditor, admin
│   ├── togo        → roles: requester, approver, auditor, admin
│   ├── liberia     → roles: requester, approver, auditor, admin
│   └── mauritius   → roles: requester, approver, auditor, admin

Note on Keycloak Authorization Services Keycloak's fine-grained Authorization Services (UMA/RPT) are deliberately not used in v1.0. OpCo-level permission enforcement is handled in Next.js middleware and Prisma query filters using the organizations claim from the standard JWT. This keeps the architecture simple and avoids operational complexity of the RPT flow at the current user scale.

Section 13

Resolved Architecture Decisions

ORM
Prisma v7 (not TypeORM). Prisma is already wired in the project; generates a fully type-safe client from the schema DSL; the @prisma/adapter-pg driver adapter supports connection pooling without external dependencies — critical for stateless Cloud Run containers. TypeORM's decorator-based approach has known friction with Next.js App Router's server/client module boundary.
IAM
Keycloak 26+ with Organizations (one Organization per OpCo, single realm). Provides native multi-tenancy, Google Workspace federation, built-in auth event audit log (login/token/role events), and platform-agnostic containerized deployment. Keycloak Authorization Services (fine-grained UMA) are explicitly skipped in v1.0 — OpCo scoping is enforced in the application layer.
Auth Client
Auth.js (NextAuth) with the Keycloak OIDC provider. Fully supported with Next.js App Router. JWT claims include OpCo organization memberships and roles — consumed by Next.js middleware for RBAC enforcement on every request.
Deployment
Platform-agnostic containerized. No cloud-provider SDK dependencies. Compatible with GCP Cloud Run + Cloud SQL or on-prem Kubernetes. Target environment to be confirmed after infrastructure decision.
Blackout Enforcement
Hard block with Emergency override. Standard changes cannot be submitted during a blackout period — the API returns an error with the blackout end date. Emergency changes bypass the block by setting isEmergency = true at submission, triggering the urgent approval path and notifying the CAB Chair immediately.
CAB Quorum
Minimum 2 CAB member approvals for high-risk changes. Enforced at the API layer by counting approvals WHERE isCab = true AND decision = 'approve' before allowing the pending → approved transition. Emergency changes require only the CAB Chair or Group Admin (single high-authority approver).
Group UX
OpCo switcher + Group Dashboard + per-OpCo drill-down. Group-level users (group_admin, group_auditor) land on a cross-OpCo summary dashboard showing aggregate KPIs. They can drill into any OpCo for full detail. A persistent OpCo switcher in the header allows switching between "All OpCos" and any individual OpCo.
