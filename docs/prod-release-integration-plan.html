CSquared Change Management — Production Release & Integration Plan

How to take the feature-complete dev branch to a running production deployment: branch integration, infrastructure provisioning, configuration, cutover, and verification.

Status: Draft — For Review · Branch model: dev = integration, prod = release · Generated 2026-06-08

Where we stand

The application is feature-complete for v1.0 on dev (all four v1.0 PRD-gap bundles + ISO P0 hardening, 325 tests green). prod is a bare baseline and a clean ancestor of dev — it is 247 commits behind with zero divergence, so the code integration is a fast-forward, not a merge with conflicts. What is not yet done is everything around the code: a production database, a production Keycloak realm, a production Google Drive, the secret set, a hosting target, and a verification pass.

P0 blocking — must exist before deploy P1 required for full function P2 post-launch / operational
Open decision (needs review before execution): the hosting target is not yet chosen. Everything below assumes a Node-capable host that can run next start (managed container/VM, or Vercel). The two material differences are: (a) whether Keycloak + Postgres are self-hosted alongside the app or managed services, and (b) how the SLA cron (POST /api/cron/sla) is triggered on a schedule. Pick the host first; the rest of this plan is host-agnostic.

Stage 1 — Provision infrastructure (P0, parallelisable)

1. Production PostgreSQL P0

Workplan: Phase 11Effort: S
Goal
A managed Postgres instance (or Accelerate URL) reachable from the app host, with automated backups and TLS.
Output
DATABASE_URL (or PRISMA_ACCELERATE_URL, which getPrisma() prefers).
Notes
Schema is applied by migration in Stage 3 — do not hand-create tables. The audit-log immutability trigger ships as migration 20260531120424_audit_log_immutability_trigger and requires the migration to run with sufficient privileges.

2. Production Keycloak realm P0

Workplan: Phase 11Effort: M
Goal
A realm (any name — the app derives it from KEYCLOAK_ISSUER, or override with KEYCLOAK_REALM) with: (1) an OIDC confidential login client; (2) the realm-roles mapper that emits realm_access.roles in the token (consumed by auth.config.ts); and (3) a separate admin service-account client for user/org operations.
Output
KEYCLOAK_ISSUER, KEYCLOAK_CLIENT_ID, KEYCLOAK_CLIENT_SECRET (login) + KEYCLOAK_ADMIN_CLIENT_ID, KEYCLOAK_ADMIN_CLIENT_SECRET (admin service account).
Acceptance
  • Login client: valid redirect URI {prod-url}/api/auth/callback/keycloak.
  • Admin client: a confidential client with service accounts enabled, granted the realm-management role manage-users on this realm — and nothing more (least privilege; no master-realm admin). The app authenticates via client_credentials, not a master admin login. (OpCo→Keycloak-org mirroring is best-effort and needs no extra role — see the deploy runbook 3b for the verified Keycloak 26.6 behaviour.)
  • The seeded admin (devops@csquared.com) can sign in and the session carries the expected realm roles + OpCo assignments.

3. Production Google Drive (service account) P0

Workplan: Phase 11Effort: S–M
Goal
A private "Change Management" Shared Drive with a service account granted Content-Manager access, and a root folder for per-change document folders.
Output
GOOGLE_SERVICE_ACCOUNT_KEY (full JSON, single line), GDRIVE_SHARED_DRIVE_ID, GDRIVE_ROOT_FOLDER_ID.
Notes
Mandatory document uploads (impact / implementation / testing / backout / solution) gate submission, so this must be live before real changes are submitted. See docs/google-drive-setup.md.

4. Email transport P1

Effort: S
Goal
Outbound notification email. Resend is primary; a Gmail/Workspace app-password SMTP path is the fallback.
Output
RESEND_API_KEY + EMAIL_FROM (preferred), or SMTP_USER + APP_PASSWORD. Leave TEST_EMAIL_RECIPIENT unset in prod (it is a dev-only redirect).

Stage 3 — Integrate & deploy

6. Branch integration: dev → prod P0

Workplan: Phase 10 (release plan) + Phase 11 (deploy)Effort: S

prod is a clean ancestor of dev, so this is a fast-forward. Tag the release so there is an immutable reference for rollback.

# verify still a clean fast-forward (no divergence)
git merge-base --is-ancestor prod dev && echo "fast-forward OK"

# integrate and tag
git checkout prod
git merge --ff-only dev
git tag -a v1.0.0 -m "CSquared CMS v1.0.0"
git push origin prod --tags

Optional: open a dev→prod PR instead of a direct push if branch protection / review is desired for the release commit.

7. Build, migrate, seed P0

Effort: S
  1. Install with the frozen lockfile: pnpm install --frozen-lockfile (project uses pnpm-lock.yaml).
  2. Build: pnpm build (runs prisma generate + next build).
  3. Apply schema: pnpm prisma migrate deploy — applies all 11 migrations, including the audit-immutability trigger. Use migrate deploy, never migrate dev, in production.
  4. Seed baseline data (6 OpCos + admin) once: run the seed against the prod DATABASE_URL. Confirm the seed is idempotent / safe to skip on re-deploys.
  5. Start: pnpm start (next start).

8. Schedule the SLA escalation cron P1

Effort: S
What
SLA breach escalation runs via POST /api/cron/sla, authorised by the x-cron-secret header matching CRON_SECRET.
How
Wire a scheduler (host cron, Vercel Cron, or external pinger) to call it on a regular cadence (e.g. hourly). Without this, SLA escalation/notifications never fire.

Stage 4 — Verify & cut over (P0)

9. Production smoke + UAT P0

Workplan: Phase 11Effort: M
Smoke (gating)
  • Keycloak login as devops@csquared.com; session has expected roles + OpCos.
  • Create a change in one OpCo, upload all 5 documents to Drive, submit (gating enforced).
  • Approve through the CAB route; SoD blocks requester=approver; audit entries written and are immutable.
  • Tenant isolation: a user from OpCo A cannot read OpCo B's change.
  • Notifications: in-app feed + email fire; trigger the SLA cron once and confirm escalation.
  • Audit CSV / PDF evidence export works for an auditor.
UAT
Business sign-off across the requester / approver / auditor / admin personas on a representative change.

10. Rollback & operational follow-ups P2

Effort: ongoing
Rollback
Redeploy the previous release tag. Schema migrations are forward-only — avoid destructive migrations; prefer additive changes so a code rollback does not require a DB rollback. Take a DB snapshot immediately before migrate deploy.
Follow-ups
  • Confirm DB backup cadence + restore drill.
  • Decide the ongoing dev→prod release cadence and whether prod gets branch protection.
  • Hand the running system to the ISMS team as evidence-generating machinery (Phase 9, separate track).
