CSquared · Change Management System

Version 2 — Roadmap & Direction

What v2 entails, why, and how we will approach it — following the completion of v1.0.

Status: v1.0 complete & in production Live at: cms.csquarednet.com Document date: 19 June 2026 Owner: Christian Koranteng

Executive summary

v1 was about breadth; v2 is about depth.

v1.0 delivered the complete change-management process end-to-end — raising a change, routing it to the right approval board, implementing it, verifying it, and closing it, all with the governance and audit evidence ISO 27001 expects. It is now live in production.

v2 does not add new process. Instead it deepens the data the system holds (moving from free-text descriptions to structured, connected information) and connects the system outward to the tools CSquared already runs as systems of record. One strategic thread runs through it: give management visibility by routing reporting through Odoo where we can.

The one-line direction
Make each change record understand what it touches and surface that understanding to the people and systems that need it — rather than relying on prose typed into a box.

Where we are today

v1.0 is feature-complete and deployed. In practical terms the system already does all of the following:

  • Secure single sign-on (company Google / Keycloak), role-based access, and full isolation between OpCos.
  • The full change lifecycle with separation-of-duties and risk-based approval boards (CAB).
  • Mandatory planning documents (impact, implementation, testing, backout, solution) before submission.
  • Immutable audit trail, per-change PDF evidence packs, compliance reporting, SLA escalation, blackout windows, a change calendar, and a systemic risk register.
  • In-app and email notifications, bilingual English / French.

Two things remain in the v1 close-out tail and are not v2 features — see “Not part of v2” below.

What v2 entails — the workstreams

Five workstreams, listed roughly by value. Each large item gets its own design cycle before any code is written.

1 Odoo integration — management visibility

Size: M → L Flagship Needs its own brainstorming cycle

What it is: push change records, status changes, and audit events into Odoo (CSquared’s primary ERP) so leadership can see what’s happening in change management without logging into the CMS.

Why it matters: it’s the most valuable item in v2 and directly answers the “management visibility” goal. It aligns with the organisational direction to route reporting through Odoo.

Range: start with a one-way push of records and status (Medium); potentially grow to a deeper, two-way sync (Large). The real questions to settle first are what data management wants to see and how we access the Odoo API — which is exactly why this gets a dedicated design cycle.

2 Structured risk & impact assessment

Size: M ISO A.8.32 · A.8.8

What it is: replace today’s single risk dropdown plus free-text impact paragraph with a proper likelihood × impact assessment and an explicit list of affected services.

Today
Risk: High · Impact: “May affect Ghana backbone traffic during cutover.”
v2
Likelihood: Possible × Impact: Major → computed risk. Affected services: Ghana Transit.

Why it matters: consistent, comparable risk scoring across all changes and OpCos — and risk the system can actually reason about, rather than words it can only display.

3 Configuration items / CMDB

Size: M → L ISO A.8.9 Foundational

What it is: a Configuration Management Database — an inventory of the “things” in our environment (landing stations, fibre links, routers, data centres, services, applications) and the relationships between them. Each thing is a Configuration Item (CI). A change would then link to real CIs instead of a free-text “infrastructure” field.

Why it matters — what it unlocks:

  • Real impact analysis: “this change touches the Accra core router → which services depend on it → who is affected?”
  • Conflict detection: two changes in the same window touching the same asset get flagged automatically.
  • Sharper routing, risk & audit: decisions key off what is changing; “show every change that touched this link” becomes a simple query.
Honest tradeoff: a CMDB is only as good as it is kept current. The payoff is real, but it adds an ongoing maintenance commitment as the network evolves — that’s a process decision, not just a feature.

4 Google Workspace directory enrichment

Size: M Tier 1 already shipped

What it is: pull richer profile fields — job title, department, office/location, manager — from the Google Workspace Directory into the user profile.

Already done in v1: “Sign in with Google” and the restriction to @csquared.com accounts shipped during the auth work. v2 only adds the directory enrichment on top, which requires Workspace admin-level access (domain-wide delegation) — hence it is deferred.

5 Smaller carried-forward improvements

Size: S–M each Opportunistic
  • Workspace defaults — pre-fill a new change request with a user’s usual OpCo, risk level, and approvers. Small UX win.
  • Severity / category routing policies — e.g. “critical changes also post to Chat and notify OpCo admins”, layered onto the existing notification settings. Build only if there is real demand.
  • Dev / test / prod environment modelling — record which environment a change targets (ISO A.8.31).

Sequencing & dependencies

The CMDB is foundational — both structured impact (#2) and richer Odoo reporting (#1) get better once configuration items exist. But the first Odoo push does not need it, and Odoo delivers the most visible value soonest. Suggested order:

  1. Odoo one-way push — fastest visible value to management; ships against data we already have.
  2. CMDB + structured risk/impact — built together (they share the “affected services” model).
  3. Directory enrichment + the smaller UX wins — fit in opportunistically.

What we deliberately left out

During the v1 review, three candidate pages were triaged and consciously not built — recorded here so the decisions are transparent:

CandidateDecisionReason
Workflow “automation” rules engineDroppedIts valuable rules (risk-based routing, SLA escalation) already exist and work; a generic configurable engine is high cost for low marginal value.
Multi-channel “alert manager”FoldedDuplicates existing email + in-app + Google Chat notifications; most channels are tools we don’t run. Any real need becomes a policy layer on existing settings.
Account-security pageIntegratedIdentity, MFA and sessions belong to Keycloak; we deep-link to its Account Console instead of rebuilding it. (Already done.)

Not part of v2 (the v1 close-out tail)

  • Production smoke testing & UAT — finishing the rollout and feedback loop now under way.
  • ISMS / compliance process — the written change procedure, evidence-of-operation, and a management-review cadence. These are organisational, owned with the ISMS team, not software features.

How we will work on v2

Each major item (Odoo and the CMDB especially) follows the same disciplined path used in v1: brainstorm → written spec → implementation plan → build with tests. Nothing schema-deepening gets built before its design is agreed, because these changes have organisation-wide implications. The natural starting point is a brainstorming cycle on the Odoo integration — the highest-value and least-defined piece.

Glossary

CMDB / CI
Configuration Management Database / Configuration Item — an inventory of IT assets and services and how they relate.
CAB
Change Advisory Board — the group that authorises changes; routing and quorum depend on risk and infrastructure type.
OpCo
Operating Company — a CSquared country/business unit; data is isolated per OpCo.
SoD
Separation of Duties — the requester cannot approve their own change; approver and implementer are distinct.
SLA
Service-Level Agreement — time targets for handling a change, with escalation when breached.
Odoo
CSquared’s primary ERP system — the intended destination for management-facing change reporting.
Keycloak / OIDC
The identity provider the app trusts for login (OpenID Connect); it owns passwords, MFA and sessions.
ISO 27001 (A.8.32 etc.)
The information-security standard; A.8.32 is its change-management control. Codes show which control each item supports.
