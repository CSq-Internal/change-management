CSquared Change Management — ISO 27001:2022 Hardening Plan

Prioritised engineering punch-list to take the application from “strong A.8.32 workflow tool” to “closes the explicit ISO control gaps.”

Scope: software changes on the dev branch · Primary controls: Clause 6.3 · A.8.32 · A.5.3 · A.8.15 · A.8.9 · A.8.31 · Generated 2026-06-06

Where we stand

The spine of an ISO-aligned change system is already built and tested (238 tests): documented requests → mandatory plan/test/rollback artifacts → CAB-routed authorization with segregation of duties → controlled lifecycle → immutable, exportable audit trail. For the core control A.8.32 we estimate ~75% coverage by feature.

P0 closest, most ISO-explicit wins P2 breadth / coherence v2.0 deferred to next release DONE already shipped
Out of scope for this engineering plan: ISO certification is an ISMS/process exercise (documented procedure, evidence of operation over time, management review). That is being clarified separately with the ISMS team — the app is the evidence-generating machinery, not the certification itself.

P0 — Do first (closest, most ISO-explicit)

1. Post-Implementation Review (PIR) P0

A.8.32 — review after changeEffort: M (≈3–4 days)Highest value

Today verified is just a status flip. ISO expects changes to be reviewed against intended outcome after implementation.

Goal
Capture a structured review when a change moves implemented → verified: outcome (success/partial/failed), verification notes, whether backout was used, success-criteria met.
Approach
Add PIR fields to ChangeRequest (or a PostImplementationReview model); gate the verified transition in updateChangeStatus (src/server/actions/changes.ts) on a completed PIR; surface it on the change-detail page + timeline.
Acceptance
  • Cannot reach verified without a recorded PIR.
  • PIR is written to the immutable AuditLog and shows in the timeline + CSV export.
  • Unit tests for the gate + a Playwright smoke (implement → PIR → verified).

2. Implementer Segregation of Duties P0

A.5.3 — segregation of dutiesEffort: S (≈1–2 days)Quick win

We enforce requester ≠ approver, but the person who approved can also mark a change implemented with no record of who implemented it.

Goal
Record the implementer and prevent the sole approver from also being the implementer (configurable per risk if needed).
Approach
Add implementedById to ChangeRequest; in updateChangeStatus for approved → implemented, set implementer and reject if the actor is the only approver on the change.
Acceptance
  • Implementer captured + shown on detail/timeline.
  • Sole-approver-as-implementer is blocked with a clear SoD error.
  • Unit tests covering the allow/deny cases.

3. Emergency-Change Workflow P0

A.8.32 — emergency changesEffort: M (≈4–5 days)

Today the emergency flag only bypasses blackout; emergency changes still need full prior approval. ISO expects a defined expedited path with mandatory after-the-fact rigour.

Goal
An expedited route: implement under emergency authority, then mandatory retrospective approval + PIR within a defined window; optionally a smaller “emergency CAB.”
Approach
Branch the lifecycle for isEmergency in changes.ts/approval-authority.ts; track retrospective-approval deadline; dashboard surfaces overdue emergency reviews.
Acceptance
  • Emergency change can be actioned fast but is flagged until retrospective approval + PIR complete.
  • Overdue retrospective reviews are visible and escalable.
  • Tests for the emergency path + retrospective gate.

A.8.32 scheduling/commsEffort: per-page S–M

Effort: M

Deferred to v2.0 (post-v1.0 release)

Valuable, but more invasive (schema-deepening) and lower-urgency than the v1 items above. Moved out of the v1 scope and scheduled for the next major version, after the v1.0 release.

7. Structured Risk & Impact Assessment v2.0

A.8.32 impact · A.8.8 vuln/assetEffort: M (≈4–5 days)
Goal
Replace the free-text impactScope + bare riskLevel enum with a small structured assessment: likelihood × impact matrix, affected services/users, derived risk score.
Approach
Add assessment fields; auto-suggest riskLevel from the matrix (still overridable); feed risk into quorum routing already in cab-quorum.ts.
Acceptance
  • Risk level is justified by a recorded assessment, not a lone dropdown.
  • Assessment visible on detail + export; tested.

8. Configuration Items / CMDB Linkage v2.0

A.8.9 — configuration managementEffort: L (≈1–1.5 wks)
Goal
Model the assets/services a change touches instead of a free-text infrastructureType, so you can answer “what changed on system X, and when.”
Approach
Introduce a ConfigurationItem model (per OpCo) + change↔CI join; keep infrastructureType as a category. Routing can later key off CI ownership.
Acceptance
  • Changes link to one or more CIs; CI history view lists its changes.
  • Migration + seed + tests.
